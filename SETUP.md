# SETUP.md

First-run setup for a fresh copy of the CoworkOS template. This file exists only until setup is finished: its last step deletes it, so a workspace that has been set up never carries these instructions, the starter menu, or anything else that belongs to the template rather than to the person using it. If this file is present, setup has not been finished yet; if it is gone, it has.

Bootstrapping the workspace this way does not need a workstation identified first the way root CLAUDE.md's Routing Protocol otherwise requires, since none exists yet. The shipped Example Workstation row in the Routing Map does not count as a real workstation for this purpose.

---

## Before starting

Say up front, once, that this setup can be paused at any point and picked up again later: nothing here has to happen in one sitting. Pausing is safe because this file stays in place until step 9 runs, so the next session sees it and resumes from wherever things were left.

Any step answered with a clear no, such as declining GitHub sync outright, is a settled decision and needs no log. Any step put off rather than decided, "not now," "later," "skip this for now," or left alone when offered, gets logged in root MEMORY.md's Open Items section (see 00_Reference/Memory System.md) with a one-line note on what is lost by leaving it that way, so a deferred step stays visible instead of quietly disappearing once this file is gone. Apply this the same way to every step below, not only the ones that call it out by name.

## Steps

0. If this AI tool is not Claude Cowork, read 00_Resources/Using CoworkOS with Other AI Tools.md before anything else, including whether this tool works from a stable folder at all. If where these files were saved is at all unclear, ask now, before creating anything, and confirm the answer back so it is on record.
1. Offer the full Starter Workstations list in 00_Resources/Workstation Setup Guide.md, not a short handful of examples. Show each area's name and its one-line gist, in order, and ask which ones to remove, if any, rather than asking the user to generate a list from nothing: most people default to two or three areas when asked to name their own, which undersells what this system is for. Make clear they can also add an area that is not on the list, rename any of these, or remove as many as they want, down to zero. Whatever is left after removals is what step 2 creates.
2. For each area kept, create a workstation following 00_Resources/Workstation Setup Guide.md: a folder with a CLAUDE.md and a MEMORY.md, nothing else until it is needed. If the area is one of the Starter Workstations, write its Identity paragraph from that area's gist and covers list, what routes here and what does not. MEMORY.md still starts genuinely empty either way, per step 4.
3. Add a row to the Routing Map in root CLAUDE.md for each new workstation, describing when to route there in the user's own words.
4. Do not create a workstation the user did not ask for, and do not pre-populate content inside one. Start empty and let it fill in through use.
5. Offer, right here rather than leaving it to be discovered later, to rename or delete Example Workstation now that real workstations exist, and to remove its row from the Routing Map. If the user would rather leave it for now, that is fine, per the deferral rule above.
6. Ask whether the user wants this workspace synced to a GitHub repository they own. This is optional and off by default; explain the reason briefly, mainly reaching the workspace from a phone or another device while away from the primary computer, and point to 00_Resources/GitHub Sync Guide.md if they say yes. Do not set this up without an explicit yes, and do not set it up before step 9 has dealt with any git history that came with the template, so their repository starts from their own workspace rather than someone else's.
7. Offer, do not wait to be asked, to set up the skills this template ships archived copies of (00_Skills/Skills Inventory.md), starting with session-audit since first-run setup already leaned on the memory system it maintains. What "set up" means depends on whether this AI tool has a real installable-skill mechanism at all; if it does, attempt it directly rather than only describing how; if it does not, or you are not sure, say so plainly and explain how the workspace still gets the same behavior without a formal install, by reading the SKILL.md file directly when triggered. Either way, this step actually happens now, not only when the user thinks to ask about skills.
8. Offer a short, clearly skippable round of questions about how the user wants written output to sound (tone, formality, anything they already know they dislike), and save what they give you to 00_Resources/voice-principles.md. Three questions at most. If they would rather skip it and let this fill in through use instead, that is a completely fine answer, per the deferral rule above, not something to push further on.
9. Hand the workspace over. Run this once every step above is either done, declined, or logged as deferred, and say what it is about to remove before removing anything. It strips out everything that belongs to the template and its author rather than to the user, so the workspace from here on is theirs alone. See "Handing over the workspace" below.

## Handing over the workspace

A copy of the template arrives carrying material that only makes sense inside the template's own repository: its README, its release history, its contribution rules and checks, placeholder example entries, and sometimes the template's git history and a git remote pointing back at the template's repository. None of that is the user's, and left in place it looks like someone else's references living inside their workspace. Remove it in this order, then confirm what was removed.

1. **Template-maintainer files.** Delete `README.md`, `CHANGELOG.md`, `CONTRIBUTING.md`, `validate.py`, and the `.github/` folder, if present. They describe how the template itself is built and contributed to, not how this workspace works; everything the workspace needs is already in root CLAUDE.md and the `00_` folders. Keep `LICENSE`: the template's license requires its copyright notice to travel with any copy, and it is the one place the template's author is named on purpose.
2. **Placeholder example entries.** Remove every line starting `Example entry:` (after the date placeholder) from root MEMORY.md, keeping the section headings and their italic guidance, and keeping any real entries written during this setup, such as deferred steps in Open Items. In ARCHIVE.md, replace the example month section with a first real entry, dated today: "Workspace created from the CoworkOS template; first-run setup completed and template files removed."
3. **Git history and remote from the template.** Only if this folder contains a `.git` folder, which means it arrived as a git clone rather than a download. Check `git remote -v`. Any remote that points at the CoworkOS template repository is not the user's: remove it with `git remote remove <name>`, since otherwise the session-audit skill's sync step would try to push this person's life into someone else's repository. Then explain that the commit history still belongs to the template, with its author's name on every commit, and recommend deleting the `.git` folder so the workspace starts clean; do it only on an explicit yes. If they said yes to GitHub sync in step 6, run 00_Resources/GitHub Sync Guide.md now, which starts a fresh history under their own name.
4. **This file.** Delete SETUP.md last, and in the same step remove the "First-time setup" subsection from root CLAUDE.md, since the only thing it does is point here. Do not keep a copy of either anywhere in the workspace; the template repository is where they live if they are ever needed again.

Finish by listing, in one short message, what was removed, what was kept and why (LICENSE), and anything logged to Open Items.
